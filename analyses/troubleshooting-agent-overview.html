Technical Overview

Troubleshooting Agent

A multi-agent AI pipeline that diagnoses, remediates, and verifies IT support issues — end to end — with a human technician in the loop.

The Pipeline
Four Agents, One Workflow
Each agent receives the output of the previous one, stored in a shared session. The full pipeline can loop when verification fails, enabling iterative troubleshooting.

Triage the ticket — detect language, analyze the problem, suggest devices

Agent Deep Dives
How Each Agent Works
Every agent is a LangChain-powered LLM with structured output, tool access, and a detailed system prompt. Responses stream to the frontend via Server-Sent Events.
🔍

Precheck Agent POST /api/v1/precheck-agent/precheck

The first responder when a technician opens a ticket. It runs a four-step sub-pipeline internally:

  • Attachment processing — vision model transcribes error screenshots into text descriptions the downstream agents can read.
  • Language & formality detection — determines the end-user's language (ISO 639-1) and communication style (casual / formal / very formal) so all future messages match tone, pronouns, and greeting conventions.
  • Ticket analysis — LLM with knowledge base access classifies: can we identify the problem? Is it device-level? Do we need more info from the user? Generates a status message for the technician and an optional response draft for the end-user.
  • Device discovery — if device-level and no device linked, the Device Finder queries previous tickets, asset management, and the common device service in parallel to suggest the most likely endpoint, ranked by confidence.

Smart caching & invalidation — results are cached per session. When a ticket gets updated (new user comment, attachment, etc.), a dedicated Ticket Change Impact sub-agent evaluates whether the delta invalidates previous work. If the user just provided the missing info you asked for, precheck reruns automatically. Administrative or irrelevant changes keep the cache intact.

Memory tool — the precheck agent can store critical findings (known bugs, company-specific configs, KB article references) in namespaced session memory for downstream agents to consume, avoiding redundant knowledge base queries.

// SSE step events (in order) "processing_attachments" "language_detection" "analyzing_ticket" "find_devices" // Structured response { canIdentifyProblem: boolean, isDeviceLevelProblem: boolean, needsMoreInformation: boolean, userResponseMessage: string, devices: [{ device, confidence, explanation }] }
📡

Observation Agent POST /api/v1/observation-agent/observe

The live diagnostics engine. This agent connects to the endpoint device via MQTT (through Resolve's QuickView / RMM infrastructure) and selectively runs device tools based on the symptoms described in the ticket.

It also has full access to the knowledge base and is explicitly instructed to search it early and often — before, during, and after device investigation — cross-referencing known issues against what it observes on the machine.

If no device is linked, the agent falls back to ticket-only analysis and knowledge base research without device tool access.

Each observation includes a severity (low / medium / high / urgent) and the agent produces an overall confidence score (0–1) and a solvable flag indicating whether the issue can be resolved remotely via RMM tools.

9 Device Diagnostic Tools — scoped to the linked device, queried via MQTT:

cpu_usageCurrent CPU utilization and load
memory_usageRAM consumption breakdown

Previous failure awareness — if this is a retry loop, the agent reads the verification.last_failure memory entry to understand what went wrong before and adjust its investigation accordingly (e.g., explore alternative root causes if symptoms persisted).

⚡

Solution Agent POST /api/v1/solution-agent/solve

Takes the observation results and generates concrete, executable remediation actions. Has access to the knowledge base (to find documented fix procedures) and the memory tool (to read what the observation agent found), but no device tools.

Output is platform-specific — determined by the linked device's OS. Scripts must be complete, production-ready, and contain zero placeholders.

Strict script rules: no try-catch boilerplate, no COM automation objects (fails under SYSTEM), must run as SYSTEM user on Windows or root on Mac, prefer built-in commands, log meaningful output for the Verification Agent to evaluate.

PowerShell Scripts WINDOWS

Automated remediation: service restarts, registry edits, file cleanup, config changes. Executed via Remote Execution Service as SYSTEM.

Virtual Technician WINDOWS

Step-by-step GUI automation for tasks that can't be scripted: app settings, browser config, user profile changes.

Shell Scripts MACOS

macOS remediation: preference resets, service management, file operations. Executed as root via Remote Execution.

Generic Actions FALLBACK

Manual instructions for the technician when no automation is possible: hardware issues, escalation paths, permission requests.

Risk assessment — every action is tagged low, medium, or high risk based on reversibility and potential for data loss. Actions are ordered with low-risk first.

Response minimalism — the agent defaults to one action. A second is added only when it covers a distinct, high-confidence remediation path. No "shotgun lists" of loosely related fixes.

Never repeats failed solutions — if a previous attempt exists (tracked in verification memory), the agent must produce a materially different approach. Failure categories guide the pivot strategy:

  • execution_error → simplify commands, break into smaller steps
  • symptoms_persist → completely different approach, don't retry
  • insufficient_permissions → adjust for actual execution context
  • partial_success → fix only the failed steps, keep what worked
  • system_conflict → handle interfering software/policies first
✓

Verification Agent POST /api/v1/verification-agent/verify

After a solution is executed, this agent validates the outcome. It analyzes execution logs, and if device access is available, re-queries device tools to check the current state against expectations.

Three possible verdicts:

  • solved — clear evidence the solution worked and the problem is resolved.
  • not_solved — evidence of errors, failures, or the problem still exists. Includes a failure object with category and root cause analysis.
  • uncertain — logs are inconclusive. Leans toward solved but recommends manual verification by the technician.

Three output audiences — the agent produces separate content for each:

  • resolutionDetails — technical markdown for internal docs and future AI agents (English)
  • resolutionSummary — 1–2 sentence plain-language outcome for the technician UI (technician's locale)
  • endUserResponse — polished message for the ticket creator, matching their language and formality level

Formality mirroring — the end-user response uses the language and communication style detected by the Precheck Agent. If the user wrote in formal German with "Sie" pronouns, the verification response does the same. If they were casual English with "Hey", the response mirrors that.

Failure taxonomy — when the verdict is not_solved or uncertain, a structured failure object is stored in session memory under the verification namespace. This feeds back into the Observation and Solution agents on the next loop:

execution_errorScript or command failed to run at all
partial_successSome steps completed, others didn't
symptoms_persistExecuted OK, but original problem remains
insufficient_permissionsAccess denied or privilege issues
system_conflictConflicting software or policies
verification_inconclusiveNot enough evidence either way

State Management
Session & Agent Memory
A single Session entity per ticket is the backbone — persisted in DynamoDB, keyed by company + ticket ID, with a 1-year TTL.

Session Entity

The session stores the full state of every pipeline phase: precheck, observation, solution, verification — each with their structured results, stream event replays, and references. It also tracks executedSolutionActions (with run IDs from Remote Execution), deviceSuggestions, cumulative tokenUsage, and the shared memory map.

The session's isStale flag is flipped by ticket updates arriving via SQS. When stale, the next agent call triggers re-evaluation rather than serving from cache.

Namespaced Memory

Each agent writes to its own namespace (precheck, observation, solution, verification) using a store_memory tool. Downstream agents receive all accumulated memories as context.

Examples of stored memories:

  • observation:finding-high-memory — "Chrome using 4.2 GB RAM with 47 tabs"
  • precheck:known-issue-vpn — "KB-2847: VPN must use IKEv2, not L2TP"
  • verification:last_failure — failure category, reason, root cause status
Frontend Experience
Technician UI Flow
The frontend is a React widget embedded in the Helpdesk via iframe. Redux manages state across 6 workflow phases, with real-time SSE streaming and frame event communication.

Happy Path (Device-Level Issue)

Ticket Opens

Widget loads, ticket ID passed in. Orchestrator hook dispatches precheck thunk.

Precheck Streams

SSE events update the progress bar: "Processing attachments… Detecting language… Analyzing ticket…"

Device Linking

If device-level and none linked, a LinkDeviceCard shows ranked suggestions. Technician selects one.

Observation Streams

Agent tool calls appear in real-time: "Checking CPU… Querying event logs… Searching knowledge base…"

Solution Generated

Action cards render: PowerShell script cards with "Start" buttons, VT plans, or generic steps.

Execute (Human in the Loop)

Technician can click the script to edit in a modal, then "Start" to execute. Status streams live from Remote Execution.

Verification

Agent checks execution logs and re-queries device. Verdict card shows: Solved, Not Solved, or Uncertain.

Resolution

CloseTicketCard shows the end-user response draft. Technician clicks "Send to Customer" to close the ticket.

Frontend Architecture

Redux State — Three Slices

  • tsaFlowSlice — core agent state: phase tracking (idle → precheck → observation → solution → verification → completed), all agent results, executed actions, device selection
  • progressSlice — UI step progress: 6 steps, each with state (open / running / error / done / info / waiting) and streaming messages
  • ticketSlice — ticket context: ID, status, linked devices

Action Card Components

  • RemoteExecutionCard — renders PowerShell/Shell scripts with edit-in-modal and execute capabilities. Shows live execution status.
  • VirtualTechnicianCard — displays goal + step list. Windows only. Editable plan, auto-executes on apply.
  • GenericActionCard — read-only manual instructions. No execution button — informational only.
  • AskMoreInfoCard — when precheck needs info. Text input for additional context.
  • CloseTicketCard — verification result with "Send to Customer" action.

Communication Layer

  • To Helpdesk — synapse-app-event: open modals (edit script, edit plan, sources), add comments, close tickets, link devices
  • From Helpdesk — synapse-frame-event: run modified script, run modified plan, session stale notification
  • Exclusive execution — only one action can run at a time; cards disable when another is in progress or ticket is closed
🔄

Iterative Troubleshooting Loop

When verification returns not_solved or uncertain, the failure details are stored in session memory. The pipeline can loop back to observation → solution → verification with full awareness of what was already tried and why it failed. Each iteration pivots strategy based on the failure category — the system never retries the same approach blindly.
