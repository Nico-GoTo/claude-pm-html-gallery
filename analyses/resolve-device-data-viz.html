Step-by-Step Execution
1
DDM authenticates with Config Lambda
On startup, the Device Data Module reads a device token from the filesystem and sends a JWT-authenticated request. The Config Lambda validates the token, checks the company ID against an environment allowlist, and returns short-lived AWS STS credentials.
GET /device/config · Bearer token · Returns AccessKeyId, SecretAccessKey, SessionToken
2
Collectors scrape system metrics on configurable intervals
The Scrape Manager runs SampleCollectors (CPU, memory, disk, network, processes, battery, temperatures, host info) and EventCollectors (Windows Event Logs). Metrics are gathered into per-epoch batches via Aggregators. The FSM-based main loop manages timing and retry logic.
gopsutil/v4 · FSM config state · Configurable scrape intervals
3
Data is compressed and serialized into FlatBuffer containers
Collected metrics are serialized to JSON, Zstd-compressed, then wrapped in a FlatBuffers container envelope with metadata: schema URL (used for routing), partition key, company/device IDs, and compression flags.
FlatBuffers · Zstd compression · Schema URL header for routing
4
Ingestion client sends batched records to Kinesis
The Ingestion package uses the STS credentials from step 1 to authenticate with Kinesis and send batched PutRecords requests. The stream operates at ~4,160 records/sec across all 250K managed devices.
aws-sdk-go-v2 · STS temp creds · PutRecords API
5
Demux Lambda routes records to type-specific downstream streams
The Demux Lambda reads each record's schema URL header and routes it to the appropriate destination Kinesis stream (metrics stream, event logs stream, software stream, etc.). Pre-allocated slices minimize heap allocations for throughput. Batches respect the 500-record / 5MB PutRecords API limits.
Pre-alloc design · 500 rec / 5MB batches · Per-schema fan-out
6
Decompression Lambda processes Firehose records to S3 / DynamoDB
Kinesis Firehose triggers the Decompression Lambda which validates payload sizes (1MB decompressed / 6MB Lambda limit), Zstd-decompresses records, and forwards to S3 buckets or error buckets. Software usage data is persisted to DynamoDB for querying.
1,000 records/invocation · 1MB decompressed limit · Error bucket routing
7
Software Lambda serves REST queries over stored data
The only currently exposed query surface: a Gin-based REST API that reads software inventory and usage history from DynamoDB. Returns installed software per device or company with daily, weekly, and monthly usage breakdowns and cursor-based pagination.
GET /devices/{company_id}/{device_id} · Paginated · Usage: last_days, last_weeks, last_months

Lambda Functions
🔐
Config Lambda
Triggered by: DDM startup · HTTP GET
Entry point for all device authentication. Validates JWT device tokens, checks company ID against the per-environment allowlist, and issues short-lived AWS STS credentials. These credentials are scoped to Kinesis PutRecords only — devices never get broader AWS access.
JWT Validation STS Credentials Company Gating Multi-env
🔀
Demux Lambda
Triggered by: Kinesis stream · event batch
High-throughput router processing ~4,160 records/sec from 250K devices. Reads each FlatBuffer record's schema URL header to determine the destination stream. Pre-allocated static slices eliminate heap allocations. Respects PutRecords limits (500 records, 5MB) and fans out to per-schema downstream streams.
Zero-alloc design Schema routing 4,160 rec/s Batch aware
📦
Decompression Lambda
Triggered by: Kinesis Firehose · batch
Handles the Firehose → S3 path. Validates that each record is within size limits (1MB decompressed, 6MB Lambda payload), Zstd-decompresses the payload, and forwards to the appropriate S3 bucket. Records that fail validation route to a dedicated error bucket for inspection.
Zstd decompress 1,000 rec/invocation Size validation Error routing
🌐
Software Lambda
Triggered by: REST API · HTTP GET
The only currently exposed query API. Gin-based REST service reading software inventory and usage history from DynamoDB. Supports company-level and device-level queries with cursor-based pagination. Returns installed software alongside daily, weekly, and monthly usage history booleans.
REST · Gin DynamoDB Pagination Usage history
Strategic Opportunities
🟢 High Impact
Agentic IT Sensing Layer
The pipeline is already collecting the right signals — CPU spikes, process anomalies, event log patterns — for an agentic system to reason over. The missing piece is a query/inference layer that lets an AI agent consume this stream and take action. The infrastructure is ahead of the product.
→ Directly enables the headless execution engine thesis
🟢 High Impact
Windows Event Log Intelligence
Event logs (failed logins, service crashes, policy changes, security events) are being collected but not surfaced as product value. Pattern detection on event IDs is a high-signal AI use case that would differentiate Resolve from simpler RMM tools — and the data is already flowing in.
→ Security positioning, alert generation, anomaly detection
🟢 High Impact
Software Usage for License Reclamation
Last-used timestamps with daily/weekly/monthly granularity are already stored in DynamoDB and queryable via API. This is directly actionable for SMB IT admins managing SaaS licenses. It's built — the question is whether it's surfaced meaningfully in the Resolve UI.
→ Near-term product value with zero new collection work
🟡 Medium-term
Nexus: Real-Time Device Context
For the Nexus vision (technician as supervisor, AI as executor), this telemetry stream is the live context that agents would consume. A technician opening a device view could have an AI agent pre-analyzing process behavior, memory pressure, and recent errors before they even ask.
→ Core input layer for Nexus agent orchestration
🟡 Medium-term
Process-Level Anomaly Detection
Per-process CPU/memory percentages and uptime are collected continuously. Baselining "normal" process behavior per device type and alerting on deviations is a natural AI feature — especially valuable for detecting ransomware precursors or rogue processes before they become incidents.
→ Proactive IT vs. reactive support — UEM differentiation
🔵 Infrastructure Gap
Query Surface is Severely Limited
Only software data is queryable today. CPU, memory, disk, network, processes, host info, and event logs all flow to S3/storage with no API on top. Any product or AI feature using this data requires building a query layer first — this is the foundational blocker for most opportunities above.
→ Prerequisite for nearly all agentic and observability features
